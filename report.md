# Technical Report: CVM++ Compiler and Virtual Machine

## 1. Introduction
CVM++ is a statically-typed, stack-based scripting language and virtual machine written in modern C++17. The architecture follows a multi-stage compilation pipeline, heavily inspired by the classic *Crafting Interpreters* model. Instead of interpreting an Abstract Syntax Tree (AST) directly, CVM++ compiles the AST into low-level bytecode, which is then executed by a high-performance stack-based Virtual Machine (VM). 

The entire system is bundled into a single binary with zero external dependencies, making it highly portable and efficient.

## 2. System Architecture
The lifecycle of a CVM++ program passes through four distinct phases:
1. **Lexical Analysis (Lexer):** Source text → Token stream
2. **Syntax Analysis (Parser):** Token stream → Abstract Syntax Tree (AST)
3. **Compilation:** AST → Bytecode (`Chunk`)
4. **Execution:** Bytecode → Stack-based VM execution

### 2.1 Lexical Analysis (`lexer.hpp`)
The `Lexer` is responsible for reading the raw source code string character by character and grouping them into meaningful `Token` objects. 
* It recognizes keywords (e.g., `let`, `fn`, `while`), identifiers, numeric literals, and operators.
* It safely ignores whitespace and comments.
* It tracks line numbers for accurate error reporting and debugging during execution.

### 2.2 Syntax Analysis (`parser.hpp`)
The `Parser` takes the flat list of tokens and constructs an Abstract Syntax Tree (AST). It uses a **Recursive Descent** parsing strategy, building nodes based on operator precedence rules (lowest to highest precedence).
* **Statements (`Stmt`):** Represent actions like variable declarations (`let x = 5;`), block scopes, `if`/`else` structures, loops (`while`, `for`), and function declarations.
* **Expressions (`Expr`):** Represent operations that produce values, such as arithmetic (`a + b`), logical comparisons, variable access, and function calls.

### 2.3 Compilation to Bytecode (`compiler.hpp`)
The `Compiler` is the bridge between the high-level AST and the low-level VM. It traverses the AST and translates it into a flat array of 8-bit instructions. 
* **Chunks:** Every function (and the top-level script itself) is compiled into an isolated `Chunk`. A Chunk contains the raw bytecode array, a pool of constant values (e.g., large numbers or function definitions), and a line-number table for debugging.
* **Locals and Scope Management:** Variables declared with `let` at the top level become globals. Variables declared inside blocks `{ ... }` or functions become locals. The compiler resolves locals entirely at compile-time by assigning them precise slots on the stack, allowing the VM to access them via fast `OP_GET_LOCAL` / `OP_SET_LOCAL` instructions rather than slow hash-map lookups.
* **Control Flow Backpatching:** When the compiler encounters an `if` or `while` statement, it must generate a forward jump (`OP_JUMP_IF_FALSE`). Because it doesn't know how far to jump until it finishes compiling the block, it emits placeholder bytes and "backpatches" the correct offset once the block's end is reached.

### 2.4 Virtual Machine (`vm.hpp`)
The VM acts as the execution engine for the generated bytecode. It is a **Stack-Based VM**, meaning operations pop inputs from a single contiguous array (the stack) and push results back onto it.

Key features of the VM include:
* **The Dispatch Loop:** The core of the VM is a highly optimized `switch` statement inside an infinite `for(;;)` loop. It fetches the next 8-bit opcode and directly executes the corresponding C++ logic (e.g., `OP_ADD` pops two values, adds them, and pushes the result).
* **Call Frames:** To support function calls and recursion, the VM maintains an array of `CallFrame` structures. When a function is called (`OP_CALL`), a new frame is pushed. A frame tracks:
  * The current function being executed.
  * The Instruction Pointer (`ip`) indicating the current byte.
  * A `slots` pointer indicating where this function's local variables begin on the global stack. 
* **Zero-Copy Arguments:** Because the `slots` pointer simply points to a higher segment of the existing stack, function arguments passed by the caller instantly become the local variables of the callee without requiring any memory copying.
* **Memory Management:** CVM++ sidesteps the need for a complex Garbage Collector (GC) by letting the Compiler own the heap allocations for functions, while value types (Int, Bool, Nil) are handled directly by the stack's lightweight tagged union (`Value`).

## 3. Advanced Features

### 3.1 First-Class Functions and Recursion
Functions in CVM++ are treated as first-class values (`Value::makeFunction()`), meaning they can be assigned to variables or passed around. All function declarations are mapped to the global namespace. This design allows trivial support for recursion (e.g., in a `factorial` function), as the function simply executes an `OP_GET_GLOBAL` to fetch itself by name before issuing an `OP_CALL`.

### 3.2 Short-Circuit Evaluation
The compiler uses intelligent jumping logic to implement short-circuit logical operators (`&&` and `||`). For example, in an `&&` condition, if the left-hand side evaluates to `false`, the compiler generates an `OP_JUMP_IF_FALSE` instruction that completely skips the execution of the right-hand side, preventing potential runtime errors (like division by zero).

## 4. Conclusion
The CVM++ architecture represents a cohesive and elegant implementation of a modern scripting language. By cleanly separating the frontend (Lexer/Parser) from the backend (Compiler/VM), the language achieves both syntactic flexibility and high execution performance. The use of a flat bytecode chunking system and a stack-based CallFrame ABI ensures that local variable resolution and recursive function calls are remarkably efficient.
